How the Karya agent store works, end to end

A B2B marketplace where finance teams run third-party AI agents on their own books, safely. Developers build and test agents in a sandbox, the platform checks what they actually do, and buyers get a signed permission statement, approval gates and a hard spend cap on every run.

Who uses it

Three sides, one execution engine

Every execution, whether a developer's test, an automated review, a buyer's free trial or a real paid run, goes through the same sandbox, the same Runtime API and the same trace. Only ownership, data source and billing differ.

Buyers

Finance teams at Indian SMBs and mid-market firms. Organised as orgs with admins and approvers.

  • Browse agents with measured scorecards
  • Try on sample data before connecting anything
  • Grant specific scopes, bind data, set a spend cap
  • Approve risky writes from web or an email link
Developers

Anyone can sign up and build. Listing publicly requires identity and business verification.

  • Write agents in Python or TypeScript with the SDK
  • agentstore push builds on platform images
  • Remote sandbox with behaviour reports
  • Earn 80% of charges, paid monthly
Karya (platform)

Owns the runtime, mediates all data and LLM access, and signs off every listing.

  • Builds and scans every bundle
  • Automated evals, red-team and cost profiling
  • Human review for anything that writes
  • Ledger, revenue split, payouts

System architecture

One monolith, one tiny bridge, bought isolation

The Spring Boot monolith stays the single source of truth. A small stateless TypeScript service exists only because E2B's template-build and in-sandbox command APIs are available only through its JS/Python SDKs. Agent code never touches buyer credentials or the internet at large; it talks to /runtime/v1.

Anatomy of one run

A bank reconciliation, step by step

What happens between a buyer clicking Run and a line appearing on their statement. The platform records every step itself; the agent no longer self-reports what it read.

  1. Reserve the spend capBuyer · ledger

    Buyer triggers the run on a connection pinned to v1.3.0. The wallet row is locked and ₹500 (the spend cap) moves from available to reserved, so concurrent runs can't overspend.

  2. Start an isolated sandboxexecution → bridge → E2B

    A fresh microVM from the agent's built template, deny-all egress plus allowlist, a 15-minute deadline and a per-run token in AGENTSTORE_RUN_TOKEN.

  3. Read only what was grantedruntime API

    GET /runtime/v1/resources/bank_statements/records → scope check → 412 rows, recorded as DATA_READ. An undeclared read returns 403 SCOPE_NOT_GRANTED; three of those kill a production run.

  4. Think through the gatewayllm gateway

    POST /runtime/v1/llm/chat with an allowed model. Tokens are metered against maxTokensPerRun and pre-checked against budget. Prompts aren't stored for production runs.

  5. Stage writes, ask for approvaldatastore · gates

    142 journal entries land as STAGED in the output store. The agent opens gate post_journal_entries and the run moves to Awaiting approval. The approver gets a web notification and an email link.

  6. Buyer decidesBuyer approver

    Approve → staged entries become COMMITTED. Reject → DISCARDED and the run is cancelled. No decision in 30 minutes → EXPIRED.

  7. Charge, clamped to the capledger

    142 invoices × ₹2 = ₹284. Buyer wallet −₹284, developer payable +₹227.20, platform revenue +₹56.80. A charge that would cross the cap is cut to the remaining amount and the run stops.

  8. Complete and clean upexecution

    Sandbox killed, the unused ₹216 reservation released, outputs downloadable from the run console. If the agent crashes or goes silent, the reaper finishes the run as FAILED, TIMED_OUT or EXPIRED.

Safety layers

Untrusted code, trusted outcome

Every agent is treated as untrusted third-party code. No single layer is relied on alone.

IsolationFresh Firecracker microVM per run, never reused across orgs.
EgressDeny-all at the VM network layer, plus a logging proxy for visibility.
Mediated accessData, LLM and gates only via /runtime/v1 with scope checks.
Short-lived tokensPer-run, hashed at rest, constant-time compare, dead at run end.
Money limitsWallet reservation, cap clamping, token budgets, developer quotas.
Version pinningConnections run only the version the buyer consented to.
Pre-publicationBuild scans, evals, red-team, scope boundary, human review for writes.
Post-publicationVitals, auto-halting rollouts, suspension, disputes.
Data handlingBuyer data never in sandbox or review runs; retention purge; SSE-KMS.

Deployment

Where it runs: AWS Mumbai, with managed pieces around it

Recommendation: put everything that stores or processes buyer data in AWS ap-south-1 (Mumbai). Buyers are Indian finance teams paying in INR, and their ledgers fall under the DPDP Act, so keeping data in-country makes the conversation with every buyer's auditor simpler. Run containers on ECS Fargate, not Kubernetes: one monolith and one small bridge don't justify cluster operations.

  • Seed: sample developer, agent, fixtures
  • Tunnel when testing real E2B

staging

  • Same shape as prod, single-AZ, smallest sizes
  • Own E2B project, LLM keys, bucket, DB
  • Deployed automatically from main

  • Multi-AZ RDS, 2+ tasks per service
  • Startup fails if dev-default secrets are present
  • Promoted manually from staging

Why not Kubernetes?Two services. Fargate gives rolling deploys, autoscaling and private networking without running a control plane. Revisit when there are more services than people.
Why not Fly.io or Render?Fine for a demo, but Mumbai data residency, KMS, private networking to RDS and IAM-scoped S3 are first-class on AWS and awkward elsewhere.
What scales first?E2B concurrency (a plan limit), then Postgres. The backend is stateless and the bridge holds no state.
Cost shapeFixed: RDS, two small Fargate services, NAT, ALB. Variable: E2B seconds and LLM tokens, both metered per run and visible on dashboards. Price it in the AWS calculator once sizes are confirmed.

Roadmap

Five milestones

Critical path: WS0 → WS5 (bridge) → WS1 (Runtime API) → WS2 (data) → WS6 (sandbox). Verification (WS7) can run in parallel at any time. The buyer-side workstreams run in the order WS13 → WS15 → WS14, and WS16 follows once money moves.

M0 · planned

Foundations

Fix execution defects (WS0), local compose, secrets, bridge skeleton.
Exit: today's run path is correct and safe.
M1

First third-party run

Build pipeline + bridge, Runtime API, buyer datasets, Python SDK. Teams and approvers (WS13), spending limits and home (WS15), email approval links (WS14).
Exit: someone else's agent runs for a buyer on uploaded CSVs.
M2

Developer sandbox

Remote sandbox, profiles, behaviour report, quotas, LLM gateway, TS SDK. Notification centre, Slack, quiet hours.
Exit: an unverified developer iterates without help.
M3

Open the doors

Verification, automated review, BYOK, docs site, production deploy. Google sign-in.
Exit: verified developers list; Tier A goes live automatically.
M4

Money & scale

Double-entry ledger, revenue split, payouts, wallet top-up and GST invoices, disputes, trials, staged rollout, vitals.
Exit: developers get paid; buyers try before connecting.

Open decisions

Needed before the named milestone

Q1
Who pays for platform LLM usage?

Settled by the UI: the developer, at cost, deducted from earnings. Buyers see only the declared unit price.

Q2
Take rate

20% default (the UI and agreement say so). Still open: 15% for partners and a developer's first ₹10 lakh of annual earnings. Needed by M4.

Q3
E2B plan, limits and region

Concurrency, template count, build minutes, and where microVMs run (data residency). Needed by M1.

Q4
Manual verification or a KYC vendor?

The admin screen shows automatic checks. The backend puts them behind a KYC provider seam: launch manual if needed, add a PAN/GSTIN/penny-drop vendor for fully automatic checks. Pick before M3.

Q6
Legal

Developer agreement, marketplace obligations, TDS/GST on payouts, DPDP processing terms, who issues buyer GST invoices. Counsel before M3 and M4.

Q9
"Ask Karya" questions in the search bar

Plain search ships first. An assistant that reads run traces is a separate, read-only design. After M2.

Q10
Can a one-tap link approve without signing in?

Yes by default: per person, single use, bound to the gate, POST-only. Each workspace can require sign-in. Confirm with the first buyers' auditors. Needed by M1.

Q11
Payment provider for wallet top-ups

Recommended: Razorpay (UPI + virtual accounts for NEFT/RTGS) behind a provider seam. Needs a merchant account and a legal check on holding prepaid balances. Needed by M4.

Q12
Slack: links or buttons?

Links only, so there is one decision path to secure. Revisit if buyers ask.
